## Host metrics (telegraf, #186)

Until #186 this machine exported **zero** non-`vector_*` series: no CPU, memory,
load, uptime, disk or thermal telemetry for the host every VM and container on it
runs on top of. It now runs a native, pinned telegraf
([`roles/telegraf_agent`](../ansible/roles/telegraf_agent/)) that remote-writes to
VictoriaMetrics on eq12_docker, stamped `host="eq12"` — the fleet-wide
`host = inventory_hostname` convention from #178.

This is a **different agent** from the telegraf *container* in the observability
compose stack on CT 101, which reports as `eq12_docker` and also carries the
TrueNAS graphite listener and the Grafana scrape. Two agents, two hosts, two
labels; neither collects the other's machine.

**Collected:** `cpu` (per-core and total), `mem`, `swap`, `disk`, `diskio`,
`net`, `netstat`, `kernel`, `processes`, `system` (load/uptime), `zfs` (ARC
kstats from `/proc/spl/kstat/zfs`), `sensors` (below), `smart` (NVMe wear,
available spare, power-on hours, media errors — 14 `smart_device_*` series), and
the ACPI fan-state exec input. Interval 60 s.

**Not** collected: package power. RAPL (`intel-rapl` `energy_uj`) is deferred to
#194 — the agent's privilege model already covers it, so it lands as a config
addition rather than a redesign. Also not collected: **fan RPM**, which this
board *can* provide via a forced `it87` binding (measured 2026-08-25) but which
is not exported and not persisted — see the fan section below for the command,
the readings, the caveats and the open decision.

### Measured sensor surface

| Source | Readings |

| `coretemp-isa-0000` | `Package id 0` + `Core 0..3` — 5 temps, each with `max`/`crit` (105 °C) and `crit_alarm` |
| `acpitz-acpi-0` | 27.8 °C |

| thermal zones | `acpitz`, `x86_pkg_temp` |

Seven `sensors_temp<N>_input` series reach the store from this host. **The number
is part of the metric name**: `remove_numbers = false` is set deliberately so
eq12's `core_0..core_3` stay four distinct series rather than merging into one,
and that keeps the digit in the field name too — the stored names are
`sensors_temp1_input` .. `sensors_temp5_input` (plus `_max`/`_crit`/`_alarm`
siblings). There is no bare `sensors_temp_input`.

### Fan speed: reachable via a forced it87 binding — measured, not yet exported

**This board has two real fan tachometers, and they have been read.** Getting at
them needs no out-of-tree code — only a `force_id` that makes the *stock* `it87`
module bind a chip it does not recognise by name. The route was found by working
through the analysis below, and it was then verified on the host.

Two things this is **not**, stated up front so nobody over-reads it: fan RPM is
**not** currently exported to VictoriaMetrics, and the override is **not**
persisted. Whether to make it permanent is an open operator decision (see
*Current status*).

**Direct enumeration under the default driver set**, 2026-08-24: no `fan*_input`
and no `pwm*` under `/sys/class/hwmon/hwmon*/`, and no Super-I/O fan driver
loaded (`lsmod` shows `coretemp` only — no `nct6775`, `it87`, `w836*`, `f718*`).
That is still true of a stock boot today; it describes the *default* state, not
the hardware's capability.

A deliberate probe followed, run through Ansible as an ad-hoc command rather than
by hand, with host snapshots taken first:

```bash
sensors-detect --auto    # MEASURED 2026-08-25
```

It **found** an `ITE IT8613E Super IO Sensors` chip at address **`0xa30`**,
confidence **9**. So there is fan hardware, hanging off that chip.

**The blocker was never a missing driver — it is a driver that does not list this
chip.** `it87.ko` ships with the installed kernel and is loadable:

```
/lib/modules/7.0.14-12-pve/kernel/drivers/hwmon/it87.ko
"IT8705F/IT871xF/IT872xF hardware monitoring driver"
```

It supports exactly 20 chip IDs — IT8603E, IT8620E, IT8622E, IT8628E, IT8712F,
IT8716F, IT8718F, IT8720F, IT8721F, IT8728F, IT8732F, IT8771E, IT8772E, IT8781F,
IT8782F, IT8783, IT8786, IT8790, IT8792, IT8795. **IT8613E is not among them**,
which is why `sensors-detect` reports the driver for this chip as
`to-be-written`.

**That list is also the way in.** IT8622E *is* on it, and the IT8613E is close
enough to the IT8622E that forcing the stock module to treat it as one works.

#### The measured result

```bash
modprobe it87 force_id=0x8622 ignore_resource_conflict=1    # MEASURED 2026-08-25
```

```
dmesg:  it87: Found IT8622E chip at 0xa30, revision 12
/sys/class/hwmon/hwmon3/fan2_input = 3792   (RPM)
/sys/class/hwmon/hwmon3/fan3_input = 1923   (RPM)
```

Two working tachometers. **Corroborated, not taken on faith:** the same binding's
temperature channels read 47/50/50/50 °C against `coretemp`'s 56 °C at the same
moment — board thermistors sitting a few degrees under the die is exactly the
right relationship, which is what distinguishes a real reading from a garbage
register.

**This beats the community consensus for this machine, and the difference
matters.** The prevailing advice for the EQ12 is to build an **out-of-tree**
`it87` driver. That is not what was done here and is not necessary: the module
above is the **stock, in-kernel `it87.ko` shipped with `7.0.14-12-pve`**, driven
by two module parameters and nothing else. No DKMS, no kernel headers, no
out-of-tree build, no tainted kernel — and nothing a kernel upgrade breaks, since
the module ships with every kernel. Do not let anyone re-derive this as "you need
the out-of-tree driver"; we measured otherwise.

#### Caveats — recorded now so a future export does not inherit them

Forcing a chip ID means the driver's register map is *approximately* right, not
exactly right. Three known discrepancies, all measured in the same run:

- **`in3` (3VSB) reads 600 mV** where the rail is ~3.3 V. That is a **fabricated
  value**, not a measurement. Any export must **exclude the bogus rails by name**
  — this repo's oldest and most-repeated trap (`_devicename_sda` reporting 0 °C;
  `amdgpu` `vddgfx`/`vddnb` at 0.000 V on N5 Pro, already excluded by a
  `tagdrop` filter in this very role).
- **`intrusion0` reports a spurious `ALARM`.** There is no chassis intrusion.
- **`pwm1`, `pwm4`, `pwm5` show `MANUAL CONTROL`** — i.e. this binding exposes
  fan *write* capability, not just read. **We are deliberately not using it.**
  The role's stance is read-only collection: no fan control, no thermal policy,
  no writes to sysfs. Exposing the capability does not change that.

#### Current status

The test was **non-persistent and has been reverted.** The module was unloaded,
nothing was written to `/etc/modules` or `/etc/modprobe.d`, a snapshot
(`rpool/ROOT/pve-1@pre-it87-force-20260825*`) was taken beforehand, and a reboot
would have cleared it regardless. eq12 has since been re-verified back to its
default state: 3 `hwmon` chips, 0 fan inputs, no `it87` loaded.

So, precisely:

- Fan RPM is **not** in this host's telemetry today.
- The capability is **proven to exist** and the exact command to reach it is
  recorded above.
- Whether to **persist** the `force_id` override and export `fan2`/`fan3` through
  the existing `telegraf_agent` role is an **open operator decision**. If
  approved it lands as a scoped follow-up — excluding the bogus rails by name,
  keeping the read-only stance. **#186 merges without it.**

**What persisting would actually cost, stated precisely so the decision is made
against the real trade-off.** The ongoing commitment is that the module claims
I/O ports at `0xa30` that **ACPI also claims** — which is exactly what
`ignore_resource_conflict=1` overrides — and it would do so on **every boot**, on
the hypervisor the whole fleet runs on. That is the thing to weigh.

It is emphatically **not** the DKMS treadmill the community route implies: there
is no out-of-tree module to rebuild on every kernel upgrade, because the driver
ships in-tree. The two commitments are easy to conflate and are not the same
shape — one is a persistent resource-conflict override, the other is a recurring
build dependency. This route carries the first and none of the second.

#### The clean path, if it ever arrives

Upstream `it87` gaining native IT8613E support would make `force_id` unnecessary
and remove the approximate-register-map caveats along with it. That is the
*clean* path — but it is no longer the *only* path, and it is not a blocker: the
`force_id` route is measured working today.

Worth noting this board had been probed once before, pre-Ansible: `/etc/modules`
already carried `# Generated by sensors-detect on Mon Sep 29 22:48:54 2025`
listing `coretemp` alone. The earlier attempt stopped at the same wall this one
did — and got past it only because the driver-versus-chip analysis above made the
`force_id` route findable.

The `sensors-detect` run itself **wrote nothing** — `/etc/modules` was
byte-identical afterwards (`--auto` defaults the write prompt to no) — and
disturbed no guest: VM 100, CT 101 and CT 104 all stayed running throughout.

### `acpi_fan_state` is binary, not a speed

Independently of the `it87` route above, the board exposes five ACPI fan objects
(`PNP0C0B:00`–`04`) as thermal cooling devices reading `Fan cur=0 max=1`. That is
**on/off state**, and it is what the agent collects today.
`roles/telegraf_agent/files/acpi_fan_state.sh` exports it as
`acpi_fan_state_state`, one series per device, values 0 or 1 — five series,
asserted by count on every deploy because the script emits *nothing* for a device
it cannot read rather than a fabricated zero, so a permissions change would show
up as four series rather than as an obvious absence.

**Never label, graph or alert on this as a fan speed.** It is not RPM, it is not
a percentage, and it is not the tachometer data described above — those are
`fan2_input`/`fan3_input` and are not currently collected.
