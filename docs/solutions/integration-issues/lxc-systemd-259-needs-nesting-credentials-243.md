# An unprivileged LXC from the Ubuntu 26.04 template (systemd 259) boots `running` with eth0 DOWN and 19 units at `status=243/CREDENTIALS` unless `nesting=1` is set

## Problem

A freshly provisioned **unprivileged** LXC on Proxmox VE 9.2.11 (host `n5pro`, CT 202
`music-workbench`, template `ubuntu-26.04-standard_26.04-1_amd64.tar.zst` — Ubuntu 26.04
LTS, systemd 259) booted with **no network** and **19 failed systemd units**, while every
coarse health signal said it was fine: `pct status 202` reported `running` and sshd was
listening on `:22`. The CT had been created with `features: nesting=0`, the role default
(`proxmox_lxc_defaults.nesting: false`,
`ansible/roles/proxmox_guests/defaults/main.yml:90`).

Two defects compounded:

1. **Declaration** — CT 202's host_vars block did not set `nesting: true`, and on a
   systemd-259 template that is not optional (see [Why This Works](#why-this-works)).
2. **Reconciliation** — the `proxmox_guests` role's "Compute LXC features drift" task
   was gated `not (item.item.unprivileged | default(proxmox_lxc_defaults.unprivileged))`
   (master, `ansible/roles/proxmox_guests/tasks/main.yml:1167`), so `features` were
   reconciled for **privileged CTs only**. An unprivileged CT received `nesting` exactly
   once, at create time, from the provisioning module; a later flip in host_vars was
   silently inert.

Proxmox told us on the very first second. Both the `vzcreate` and `vzstart` task logs
carried `WARN: Systemd 259 detected. You may need to enable nesting.` (`TASK WARNINGS: 1`).
Nobody read them. All facts below were measured 2026-09-02.

## Symptoms

Inside the CT (`pct exec 202 -- …`):

```text
$ ip -4 -br addr
lo               UNKNOWN        127.0.0.1/8
# eth0@ifN is present but DOWN; no 192.168.30.16/18

$ networkctl
... eth0   ether   ... unmanaged

$ systemctl is-active systemd-networkd
failed

$ systemctl --failed
# 19 units, every one of them:
#   (code=exited, status=243/CREDENTIALS)
# systemd-networkd, systemd-resolved, systemd-journald, systemd-journal-flush,
# systemd-sysctl, systemd-sysusers, systemd-tmpfiles-setup,
# systemd-tmpfiles-setup-dev, systemd-tmpfiles-setup-dev-early,
# systemd-network-generator, systemd-udev-load-credentials, systemd-firstboot,
# plus their .socket units
```

On the host:

```text
$ ip link show veth202i0
... state LOWERLAYERDOWN

$ pct config 202 --current | grep features
features: nesting=0

$ grep WARN /var/log/pve/tasks/…/UPID:n5pro:…:vzcreate:202:…
WARN: Systemd 259 detected. You may need to enable nesting.
# identical line in the vzstart task log
```

The status code is the tell: `243/CREDENTIALS` on *every* failed unit, not a
networkd-specific error. The network was collateral — journald, sysctl, tmpfiles and
sysusers were equally dead.

## What Didn't Work

- **Trusting `pct status`.** `running` means the init process is up, nothing more. sshd
  starting (it does not load credentials) made the CT look reachable from the host while
  it had no address on the LAN.
- **Checking the network config.** PVE had autogenerated
  `/etc/systemd/network/eth0.network` inside the CT with the correct `Address=` and
  `Gateway=`. The config was right; the daemon that would consume it could not start.
  Reading config files answers "is it declared?", never "is it running?".
- **Reading `pct config 202 --current`.** It faithfully reported `nesting=0` — that IS
  the defect, but nothing in that output says it is one. Without the task-log WARN line
  there was no pointer from "feature off" to "systemd broken".
- **Expecting `task infra:hosts` to converge a host_vars change.** With the privileged-only
  gate on the drift compute, flipping `nesting: true` in host_vars and re-running the role
  would have reported green and changed nothing on the CT.

## Solution

Two changes on branch `feat/254-workbench-lxc` (#254, pending merge as of this writing).

**1. Declare nesting for the CT** — `ansible/inventory/host_vars/n5pro/vars.yml:292-307`:

```yaml
# before
  - vmid: 202
    hostname: music-workbench
    os: ubuntu-26.04
    unprivileged: true
    # (no nesting key → proxmox_lxc_defaults.nesting = false)

# after
  - vmid: 202
    hostname: music-workbench
    os: ubuntu-26.04
    unprivileged: true
    # REQUIRED for this template, not a nicety: Ubuntu 26.04 ships systemd 259,
    # which in an unprivileged CT without nesting fails every early unit with
    # status=243/CREDENTIALS (networkd, journald, sysctl, tmpfiles…) — measured
    # 2026-09-02 … Nesting on an unprivileged CT is not a privilege escalation
    # (it is the userns-confined kind).
    nesting: true
```

**2. Reconcile features for unprivileged CTs too** — "Compute LXC features drift",
`ansible/roles/proxmox_guests/tasks/main.yml:1156-1193`:

```yaml
# before (master, main.yml:1160-1168)
  when:
    - item.rc == 0
    # Privileged only — unchanged gate. Unprivileged CTs get `features` at CREATE
    # time from the provisioning module and are not reconciled here; …
    - not (item.item.unprivileged | default(proxmox_lxc_defaults.unprivileged))
    - live_norm != desired_norm

# after (feat/254-workbench-lxc, main.yml:1182-1193)
  when:
    - item.rc == 0
    # Reconciled for privileged AND unprivileged CTs since #254. …
    - live_norm != desired_norm
```

`desired_features` (main.yml:1166-1169) still adds `mount=nfs` only when `nfs_enabled`
is set, and the existing `nfs_enabled` assert keeps that privileged-only — so for an
unprivileged CT the reconciled string is exactly `nesting=N`.

**Apply and verify.** On the running CT the reconcile issues
`pct set 202 -features nesting=1`, which lands as **pending** (features apply at start),
so a stop/start followed:

```text
$ pct stop 202 && pct start 202
$ pct exec 202 -- ip -4 -br addr
lo     UNKNOWN  127.0.0.1/8
eth0   UP       192.168.30.16/18
$ pct exec 202 -- systemctl --failed
0 loaded units listed.
$ pct exec 202 -- ping -c1 192.168.23.1     # gateway reachable
```

A later destroy + recreate with `nesting: true` in host_vars came up healthy at first
boot — the provisioning module sets nesting at create, and the drift compute now guards
it for the CT's whole life.

## Why This Works

Per Proxmox's own warning (`Systemd 259 detected. You may need to enable nesting.`),
recent systemd releases depend on facilities that an unprivileged container is denied
unless `nesting=1` is set. What was observed: every unit that participates in systemd's
credentials mechanism — which on this release includes networkd, resolved, journald,
sysctl, sysusers, tmpfiles, firstboot and their sockets — exited with
`status=243/CREDENTIALS`, and every one of them came up clean the moment nesting was
enabled, with no other change. The consistent reading is that the credentials setup
needs mount operations (its own private tmpfs) which the default unprivileged
confinement refuses; `nesting=1` grants them. We did not trace the exact syscall that was
refused, and this document does not claim to.

On the security question: `nesting` on an **unprivileged** CT is the user-namespace-
confined kind — it lets the guest's init mount things within its own userns. It is not
the privileged-CT nesting that the Docker-in-LXC gotchas are about, and it is not a
privilege escalation against the host.

On the reconcile half: the old gate encoded a contract ("unprivileged CTs get features at
create, never touched again") that was correct only while `nesting` was a nicety. Once a
template makes it mandatory, a host_vars flip that never reaches `pct set` is a silent
no-op of exactly the kind this repo has been bitten by before (see Related Issues).
Removing the clause makes the drift compute do for unprivileged CTs what it already did
for privileged ones; the `nfs_enabled` assert remains the privileged-only guard for the
one feature that *is* a privilege boundary.

## Prevention

- **Treat `nesting: true` as required for any unprivileged CT on a modern-systemd
  template** — Ubuntu 24.04+/26.04, Debian 13 and later. The role default stays `false`
  (`ansible/roles/proxmox_guests/defaults/main.yml:90`), so the declaration is per-CT; write the reason beside it, as
  CT 202's block does.
- **Read the task log WARN lines.** `vzcreate` and `vzstart` logs under
  `/var/log/pve/tasks/` (and the Proxmox UI task viewer) carried the answer before the
  first symptom existed. `TASK WARNINGS: 1` on a green task is a finding, not noise.
- **Verify a fresh CT from the inside, not from `pct status`:**

  ```bash
  pct exec <id> -- systemctl --failed     # expect: 0 loaded units listed
  pct exec <id> -- ip -4 -br addr         # expect: eth0 UP with the declared address
  ```

  `pct status` and a listening sshd both survive a broken early boot.
- **A host_vars flip must converge.** The role now reconciles `features` for unprivileged
  CTs (`ansible/roles/proxmox_guests/tasks/main.yml:1182-1193`); a changed `nesting` value shows as drift in `--check`
  and is applied via `pct set`. Remember the apply is *pending* on a running CT — the
  role reports it, the operator schedules the restart.
- **`243/CREDENTIALS` across many unrelated units is a container-capability symptom**, not
  a per-service bug. Do not debug networkd; check the CT's features first.
